# CC Apply

Read the migration plan generated by cc-learn and execute code modifications item by item.

For data path and format conventions, see [../../data-contracts.md](../../data-contracts.md).

<OUTPUT-BOUNDARY>
This skill modifies project source code according to the migration plan.
It also updates `docs/cc-context/plans/*-migration-plan.md` (status and item markers only).
It does NOT write to `docs/cc-context/knowledge/` or `docs/cc-context/traces/` — those belong to cc-learn and cc-trace respectively.
It does NOT create new migration plans or verification reports.
</OUTPUT-BOUNDARY>

<ADAPTATION-BOUNDARY>
"Code-level adaptation" means adjusting implementation details (variable names, import paths, API signatures) to fit the current codebase. It does NOT mean:
- Adding migration items not in the plan
- Changing the architectural approach of a migration item
- Modifying files not listed in the item's "Affected files"
- Refactoring surrounding code beyond what the migration item requires

If adaptation requires changes beyond the above scope, STOP and inform the user before proceeding.
</ADAPTATION-BOUNDARY>

## Prerequisites

`docs/cc-context/plans/*-migration-plan.md` must exist (generated by `/cc-learn`). Use Glob to find the latest:

```
docs/cc-context/plans/*-migration-plan.md
```

If not found, tell the user to run `/cc-learn` first.

### Status Check

After loading the plan, **you must check the status field** in the document:

| Status | Action |
|--------|--------|
| `draft` | **Stop execution.** Tell the user: "Plan is not yet confirmed (status: draft). Please run /cc-learn to complete review and confirmation." |
| `confirmed` | Proceed with execution, update status to `in-progress` |
| `in-progress` | Resume execution on incomplete items (checkpoint recovery) |
| `completed` | Tell the user: "All migration items have been executed. Consider running /cc-verify to validate the results." |
| `verified` | Tell the user: "Plan has been completed and verified." |

## Workflow

### Step 1: Load Migration Plan

Use Glob to find all `docs/cc-context/plans/*-migration-plan.md` files. Sort matches lexicographically and pick the last one (most recent date). If multiple plans exist with non-terminal statuses (`confirmed` or `in-progress`), warn the user and ask which to use.

Read the selected plan, check the status, and extract all migration items. Each item should contain:
- Corresponding CC pattern
- Reference example (link to knowledge/examples/)
- Current status (partially-implemented / missing)
- Target implementation
- Affected files
- Specific steps
- Priority and complexity

### Step 2: Sort by Priority

Sort by HIGH → MED → LOW, then by complexity S → M → L within the same priority level.

Skip items already marked with ✅ (checkpoint recovery scenario).

### Step 3: Execute Item by Item

For each migration item:

1. **Announce the current item** — Tell the user which item is being executed
2. **Read affected files** — Understand the existing code
3. **Consult reference examples** — If the migration item links to a reference example in knowledge/examples/, read it to understand the concrete CC implementation
4. **Execute the migration** — Follow the plan's specific steps, adhering to plan intent with necessary code-level adaptation
5. **Report results** — Show what was changed and which files were modified
6. **User confirmation** — Wait for user confirmation before proceeding to the next item

**Code-level adaptation principles:**
- When plan steps diverge from actual code, follow the plan's intent and adapt to the current code structure
- Use reference examples as concrete guidance, not as code to copy verbatim
- Follow the project's existing code style (naming, indentation, import style, etc.)
- If adaptation requires significant deviation from the plan, inform the user before proceeding

### Step 4: Update Plan Document

After completing each item, mark it as done in the migration plan document (append ✅ to the item heading).

If an item cannot be executed (code has changed, dependencies missing, etc.), mark it with ⏭️ and record the skip reason.

After all items are complete, update the status to `completed`.

### Step 5: Output Summary

```
CC Apply complete!
  Items executed:    X / Y
  Skipped:           Z items
  Files modified:    N
  Plan status:       completed
  Suggested next:    Run /cc-verify to validate migration results
```

## Execution Reference

For API format translation and pattern-level migration strategies, see [references/migration-strategies.md](references/migration-strategies.md).

## Key Principles

- **Plan-guided** — Follow plan intent, allow necessary code-level adaptation
- **Example-informed** — Consult knowledge/examples/ for concrete CC implementation reference
- **Status-driven** — Only execute confirmed or in-progress plans; reject all other statuses
- **Confirm per item** — Wait for user confirmation after each migration item
- **Respect existing code** — Follow the project's code style and architecture patterns
- **Reversible** — Each migration item should be independently reversible
- **Checkpoint recovery** — Support resuming from the point of interruption
- **On blockage** — Mark with ⏭️ and record the reason; do not force modifications
